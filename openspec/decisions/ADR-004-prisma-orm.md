# ADR-004: Prisma as the ORM

## Status
Accepted

## Context
Ingexpert uses PostgreSQL (hosted via Supabase) as its database. The backend (`apps/api`) requires a type-safe way to query and mutate data, handle schema migrations, and deal with PostgreSQL-specific types like `Decimal` (used for stock quantities).

Options considered:
- **Raw SQL with `pg` driver** — maximum control but no type safety; queries drift from the schema without a compile-time signal.
- **TypeORM** — mature but relies on decorators and its type inference is weaker; entity classes duplicate Prisma's generated types.
- **Drizzle ORM** — newer, SQL-like API, good TypeScript support, but smaller ecosystem and fewer migration tools at the time of decision.
- **Prisma** — schema-first with a declarative `.prisma` file; generates a fully-typed client; strong migration tooling; first-class `Decimal` type support.

## Decision
Use **Prisma** as the ORM, with all schema files located in `packages/database/prisma/schema/`.

- `pnpm db:generate` regenerates the Prisma Client after any schema change.
- `pnpm db:migrate` applies pending migrations to the database.
- The generated `PrismaClient` is re-exported from `packages/database` and injected via NestJS DI as `PrismaService` — never instantiated directly in a module.
- `Decimal` fields (e.g., `stock` on `Item`) are mapped to TypeScript's `Prisma.Decimal` type; service mappers convert them to `number` before returning to clients.
- Stock mutations MUST use `prisma.$transaction` to ensure atomicity between stock updates and movement record creation.

## Consequences
- **Easier:** The generated Prisma Client is fully typed — adding a column without updating the service mapper causes a TypeScript compile error.
- **Easier:** Migrations are version-controlled SQL files generated by `prisma migrate dev`, making schema history auditable.
- **Easier:** Prisma Studio (`pnpm db:studio`) provides a visual database browser for development.
- **Harder:** Every schema change requires running `pnpm db:generate` to refresh the client — skipping this step causes stale type errors that can be confusing.
- **Harder:** `Prisma.Decimal` requires explicit conversion to `number` in all service mappers; forgetting this causes serialisation issues when returning data over JSON.
